# Portfolio production deployment

## 1. Final architecture

Production runs from `docker-compose.prod.yml` with one loopback-only ingress:

```text
Mac -> GitHub main -> GitHub Actions -> dedicated self-hosted runner
                                             |
                                             v
Cloudflare -> Cloudflare Tunnel -> 127.0.0.1:${PUBLIC_PORT}
                                             |
                                             v
                                      Nginx / React
                                       |         |
                         /api, /admin  |         | /static, /media
                                       v         v
                                  Gunicorn     volumes
                                       |
                                       v
                                  PostgreSQL
```

- `/` serves the Vite production bundle.
- `/api/` and `/admin/` are proxied to Django through Gunicorn.
- `/static/` and `/media/` are served by Nginx from persistent volumes.
- PostgreSQL and Gunicorn are private Docker services with no published host ports.
- Only Nginx binds to `127.0.0.1:${PUBLIC_PORT}`. Cloudflare Tunnel is the public entry point.

## 3. Production environment variables

Create a server-only file outside the runner checkout using `.env.example` as the template.

Required values:

| Variable | Purpose |
|---|---|
| `PUBLIC_PORT` | Unused loopback port consumed by Nginx and Cloudflare Tunnel |
| `DEBUG=false` | Disables Django development behavior |
| `SECRET_KEY` | Unique, high-entropy Django key |
| `ALLOWED_HOSTS` | `portfolio.mosquerasoft.com` |
| `CSRF_TRUSTED_ORIGINS` | `https://portfolio.mosquerasoft.com` |
| `DB_NAME` | PostgreSQL database name |
| `DB_USER` | PostgreSQL user |
| `DB_PASSWORD` | Strong PostgreSQL password |

Optional tuning values are documented in `.env.example`: Gunicorn workers, threads, timeout and log level.

The real file, its secrets, the runner registration token and the Cloudflare Tunnel token belong only on the server or their respective provider. They must never enter Git.

## 4. Security action required

The previous `backend/compose.yml` contained a hardcoded PostgreSQL password. Removing the file does not remove that value from Git history. Rotate the password anywhere it was used. If the repository has ever been public or shared, consider rewriting the secret from history separately and coordinate that rewrite before force-pushing.

## 5. One-time Ubuntu preparation

The following placeholders remain intentionally unresolved:

- `<RUNNER_DIRECTORY>`: dedicated directory for this repository's runner.
- `<RUNNER_USER>`: dedicated unprivileged Linux user.
- `<PRODUCTION_ENV_FILE>`: absolute path outside the checkout.
- `<PUBLIC_PORT>`: an unused loopback port.
- Runner registration token: generated by GitHub and short-lived.
- Cloudflare Tunnel ID/token: configured later in Cloudflare.

Docker Engine with the Compose v2 plugin must already be installed and enabled:

```bash
docker version
docker compose version
```

Create the server-only configuration directory and file:

```bash
sudo install -d -m 750 -o <RUNNER_USER> -g <RUNNER_USER> "$(dirname <PRODUCTION_ENV_FILE>)"
sudo -u <RUNNER_USER> install -m 600 /dev/null <PRODUCTION_ENV_FILE>
sudo -u <RUNNER_USER> editor <PRODUCTION_ENV_FILE>
```

Copy the keys from `.env.example`, choose `<PUBLIC_PORT>`, and generate `SECRET_KEY` without saving it to shell history:

```bash
python3 -c 'import secrets; print(secrets.token_urlsafe(64))'
```

The runner user needs Docker access:

```bash
sudo usermod -aG docker <RUNNER_USER>
```

Log out and back in before testing Docker as that user. Docker group membership is effectively root-equivalent; use a dedicated runner user and do not reuse this runner for untrusted repositories.

## 6. Dedicated GitHub Actions runner

In GitHub open:

`Repository -> Settings -> Actions -> Runners -> New self-hosted runner`

Choose Linux and the server architecture. GitHub generates current download, checksum and registration commands. Run those exact generated commands as `<RUNNER_USER>` inside `<RUNNER_DIRECTORY>`; do not copy a stale runner version or registration token from documentation.

Register this runner at **repository level**, not organization level. That keeps it dedicated to this portfolio. The workflow uses the standard labels `self-hosted`, `linux` and `x64`; use the architecture label GitHub assigns if the server is ARM64.

After `./config.sh` succeeds, install it as a persistent systemd service:

```bash
cd <RUNNER_DIRECTORY>
sudo ./svc.sh install <RUNNER_USER>
sudo ./svc.sh start
sudo ./svc.sh status
```

On Ubuntu systems using `needrestart`, follow GitHub's runner documentation to exclude the runner service from being restarted in the middle of a job.

Configure the GitHub **production environment variable**:

```text
Name:  PRODUCTION_ENV_FILE
Value: <absolute server path chosen above>
```

This value is a path, not the file contents. Secrets remain on the server.

## 7. Initial source preparation

Do not maintain a hand-edited production clone. `actions/checkout` creates and updates the runner workspace to the exact GitHub commit. GitHub remains the source of truth.

The initial deployment is triggered by either:

1. merging/pushing the production change to `main`; or
2. opening `Actions -> Deploy production -> Run workflow -> deploy`.

The first deployment builds both images, creates the named volumes, migrates PostgreSQL, collects static files and waits for all healthchecks.

## 8. Current SQLite data

Development continues to use SQLite when `DB_NAME` is absent. Production uses PostgreSQL.

No SQLite data is imported automatically. If the existing local content must be copied, perform a reviewed one-time export/import before public launch:

```bash
# Mac, from backend using SQLite
python manage.py dumpdata --natural-foreign --natural-primary \
  --exclude contenttypes --exclude auth.permission --indent 2 > portfolio-data.json
```

Transfer that file securely, load it through a temporary backend container, validate it, and delete the transfer file. Do not commit the dump because it can contain contact inquiries or other personal data.

## 9. Cloudflare Tunnel

After the application is healthy, create a published application route in the existing tunnel:

```text
Public hostname: portfolio.mosquerasoft.com
Service type:    HTTP
Service URL:     http://127.0.0.1:<PUBLIC_PORT>
```

Cloudflare handles public TLS. No router port or public Docker port is required. Do not put the Tunnel ID or token in this repository.

Consider protecting `/admin/` with Cloudflare Access in addition to Django authentication.

```bash
curl --fail -H 'Host: portfolio.mosquerasoft.com' \
  -H 'X-Forwarded-Proto: https' \
  http://127.0.0.1:<PUBLIC_PORT>/api/health/

```

Publicly:

```bash

curl --fail https://portfolio.mosquerasoft.com/api/health/
```

Also verify `/`, `/projects`, `/admin/`, a `/media/` image and the CV download.

## 11. What happens on every push to main

1. GitHub serializes deployments through the `portfolio-production` concurrency group.
2. A GitHub-hosted runner executes Django checks/tests and frontend lint.
3. If validation fails, the production runner is never invoked.
4. The dedicated self-hosted runner checks out the exact commit.
5. The deploy script validates Compose and the server-only env file.
6. It snapshots current application image tags for rollback.
7. It rebuilds only services affected by the Git diff; Docker layer cache is preserved.
8. PostgreSQL is started/checked, migrations run and static files are collected.
9. Compose replaces services and waits for healthchecks.
10. If startup fails, previous application images are restored automatically.
11. Dangling images older than seven days are removed; volumes are never pruned.

## 12. Logs and diagnosis

GitHub job output is available under `Actions -> Deploy production`.

On the server:

```bash
docker compose --project-name portfolio --env-file <PRODUCTION_ENV_FILE> \
  -f docker-compose.prod.yml ps
docker compose --project-name portfolio --env-file <PRODUCTION_ENV_FILE> \
  -f docker-compose.prod.yml logs --tail=200 backend frontend db
docker compose --project-name portfolio --env-file <PRODUCTION_ENV_FILE> \
  -f docker-compose.prod.yml logs --follow backend frontend
```

Gunicorn and Django log to stdout/stderr so they appear in Docker logs.

## 13. Rollback

Preferred method without SSH:

`Actions -> Deploy production -> Run workflow -> rollback`

Manual server fallback:

```bash
cd <current runner checkout>
PRODUCTION_ENV_FILE=<PRODUCTION_ENV_FILE> ./scripts/rollback.sh
```

Rollback retags the immediately previous backend/frontend images, recollects compatible static files and runs `compose up --wait`. It does **not** reverse database migrations. Before deploying destructive migrations, create a database backup and define the reverse migration explicitly.

## 14. Backup scope

Back up these named volumes/configuration:

- `portfolio_postgres_data`: mandatory database backup using `pg_dump`.
- `portfolio_media_data`: uploaded project images and CV.
- `<PRODUCTION_ENV_FILE>`: encrypted secret/configuration backup outside Git.
- Cloudflare Tunnel configuration/token through the chosen secure secret process.

`portfolio_static_data` is rebuildable with `collectstatic`; Docker images and the runner checkout are reproducible and do not require backup.

## 15. Manual versus automated

Manual once:

- rotate the exposed PostgreSQL password;
- install/verify Docker and Compose;
- create the dedicated user, env file and repository runner;
- install the runner service;
- select `PUBLIC_PORT` and configure `PRODUCTION_ENV_FILE` in GitHub;
- import existing SQLite content if required;
- configure the Cloudflare published hostname;
- create the initial Django superuser.

Automated afterward:

- checkout from GitHub;
- tests and lint;
- selective image builds;
- migrations and `collectstatic`;
- container replacement and health validation;
- automatic image rollback on failed startup;
- safe dangling-image cleanup;
- serialized deployments from every push to `main`.
